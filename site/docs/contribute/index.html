Contribute

Bug reports, ideas and pull requests are welcome. This page covers how to report a problem, what a pull request has to pass, how to build and test the project, and the gpui traps that cost the most time.

Filing an issue

  • Search existing issues first.
  • Use the bug report form. It asks for the Openify version, Windows version, display scale and the log file. Reports without a log are usually not actionable.
  • Feature requests work best when they describe the problem first and the solution second.
  • For a security problem, do not open a public issue. See Privacy and security.

The logs live in %LOCALAPPDATA%\Openify (paste that into the Explorer address bar): openify.log and, after a crash, crash-<time>.txt. Attach both. For more detail, start the app from a terminal with debug logging:

PowerShell
$env:RUST_LOG="openify=debug"
.\target\release\openify.exe

Never post tokens or your Spotify credentials. An issue never needs them.

Pull requests

  1. For anything larger than a small fix, open an issue first so the design can be agreed before you spend time on it.
  2. Branch from master and keep the PR focused on one thing.
  3. Run the checks below locally before you push.
  4. Describe what changed, why, and how you verified it. For a UI change, attach a screenshot. For a performance-sensitive change (render loop, audio path, memory), include a measurement next to the bar it had to meet.
  5. By contributing you agree your work is licensed under GPL-3.0-or-later.

The PR template asks for the same things: what and why, how you checked it, and a short checklist (build and tests pass, new text is in the i18n table in both languages, tests do not touch Spotify or your real settings).

What CI checks

CI runs on every pull request and on pushes to master. A change should pass all of it.

JobWhat it runs
Build, test, lint (Windows)cargo build --release --locked, cargo test --release --locked, cargo fmt --check, cargo clippy --release --locked --all-targets -- -D warnings
Windows ARM64A release build for aarch64-pc-windows-msvc
cargo-denyLicenses, bans and sources must pass. Advisories are checked too, but do not block yet.
Vendor driftA report of how the vendored crates differ from crates.io (scripts/vendor-diff.ps1)

The ARM64 job exists because Openify ships an ARM64 installer. If you add a dependency with native code, check that it builds for that target.

Conventions

The full reasoning is in How it works. The short version:

  • New features are their own gpui Entity. Do not add fields to Shell, which is already too big.
  • The engine never produces user-facing text. It sends typed codes (Event variants, notice kinds) and the UI turns them into words.
  • Nothing blocks the render path. No network, no long disk work, no waiting on a lock held by background work.
  • Design rules are tests. src/ui/design_rules.rs fails the build if you use raw spacing, radius, font size, shadow or color values instead of the variables in src/ui/theme.rs, or an icon_button("...") without a .tooltip(. Use the components in src/ui/components.rs. See Design.
  • Pure core, thin shell. Put decisions in side-effect-free functions with unit tests (queue.rs, recovery.rs, login.rs) and keep I/O at the edges.
  • Vendored crates are patched copies. Mark every changed line with an OPENIFY: comment and document it in that crate's OPENIFY.md. scripts/vendor-diff.ps1 checks drift.
  • Be polite to Spotify. Do not add code paths that hammer its internal endpoints. Reuse the shared rate gate and caches. Tests must not talk to Spotify; use fixtures in src/engine/fixtures or OPENIFY_TEST_FAKE_PLAY=1.
  • Settings in tests. A test that touches settings uses OPENIFY_SETTINGS_PATH with a temporary file, never your real %APPDATA%\Openify\settings.json.
  • Comments explain why. Keep functions small.
  • New dependencies need a reason. Check the license is GPL-3.0 compatible with cargo deny check licenses.

Internationalisation

Every UI string lives in one table, src/i18n/table.rs. English and Turkish sit side by side in a single macro entry, so a missing translation is a compile error rather than a blank label at runtime.

In code, use the t!, tf! and tp! macros (plain text, formatted text, plurals; the header of src/i18n.rs explains each). Do not hard-code user-visible strings anywhere else. The app name comes from src/brand.rs.

Two tests guard this. src/i18n/tests.rs checks placeholders, plurals and empty strings, and no_raw_turkish_text_in_sources fails if a string literal in code contains Turkish letters (comments and log lines are exempt). To add a whole new language, extend the table and the language setting.

To try a language without changing your settings, set OPENIFY_TEST_LANG=en or tr in a test run.

Building from source

You need Windows 10 or 11, Rust (rustup installs the version pinned in rust-toolchain.toml on the first build), the MSVC build tools with the "Desktop development with C++" workload, the Windows SDK and Git. No .env file or API key is needed.

PowerShell
git clone https://github.com/FurkanKY/Openify.git
cd Openify
cargo build --release
.\target\release\openify.exe

The first build compiles gpui and its dependencies and takes a while. If a running Openify locks target/, build to another directory with --target-dir and run a copy of the exe.

Running the tests

PowerShell
cargo test --release
cargo clippy --release -- -D warnings
cargo fmt --check

cargo build and cargo test should finish without warnings, apart from known old ones from vendor/librespot-core and proc-macro-error2.

Tests are ordinary unit tests inside the modules (queue, recovery, login, output ring, edit queue, i18n, settings, cache and more). They use fixtures and fake backends and never touch Spotify or your real settings.

A few tests are marked #[ignore] and hit a real account, for example friend activity, radio, track credits and library writes. They never run automatically. Only the account owner should run them, on purpose.

Test hooks

A test run is a run of the app with OPENIFY_TEST_DISPLAY or OPENIFY_SETTINGS_PATH set. It starts offline with its own temporary folders and never touches your real settings, cache or Spotify account unless you pass OPENIFY_TEST_ONLINE=1. None of these variables changes behavior for normal users. The most useful ones:

VariableWhat it does
OPENIFY_TEST_DISPLAY="w,h"Opens the window on a non-primary monitor without taking focus, and makes the run a test run. Closes itself after 15 minutes.
OPENIFY_SETTINGS_PATH=<file>Uses this settings file instead of the real one.
OPENIFY_TEST_CACHE_DIR=<folder>Puts the whole cache folder there. Without it a test run uses %TEMP%\openify-sandbox.
OPENIFY_TEST_FAKE_PLAY=1Pretends to play without sending anything to Spotify.
OPENIFY_TEST_OFFLINE=1Starts offline. With an empty cache, Home, Explore and Library show the offline state.
OPENIFY_TEST_LANG=en|trForces the interface language.
OPENIFY_TEST_THEME=light|darkForces a palette in an isolated test run without changing the saved preference.
OPENIFY_TEST_VIEW=<page>Opens a page or panel after a delay: now, home, settings, queue, help, search:<query> and more.
OPENIFY_TEST_SCALE=<0.5-4>With OPENIFY_TEST_DISPLAY, forces the window scale (1.25, 1.5 and 2 simulate 125 to 200% displays).
OPENIFY_LOG_DIR=<folder>Moves the log and crash report folder.
OPENIFY_INSTANCE_ID=<name>Namespaces the single-instance lock, so you can test next to your own running Openify.
RUST_LOG=openify=debugStartup timings, audio device and format, queue targets.

Several features also read recorded responses from a JSON fixture (friend activity, track credits, lyrics, radio, search), so you can see every state without a network. The complete list, including measurement hooks for frame time, memory and the audio output, is in docs/TESTING.md.

When you measure, run a copy of the exe, stay off the real account, and report the measured value next to the threshold it had to meet.

gpui pitfalls

Openify is built on gpui 0.2.2. These are the problems that cost the most time. The full list is in docs/TESTING.md.

Wheel handlers do no hit testing
A capture-phase on_mouse_event that checks bounds.contains(position) also takes the wheel meant for a layer on top (queue or lyrics panel). Use smooth_scroll::wheel_zone. A layer that covers content uses .occlude(); one that should let the wheel through uses .block_mouse_except_scroll().
Text truncation
truncate() caches its first measurement, and line_clamp crashes on multi-byte characters. Use the own Line element in src/ui/text.rs.
Single-line text in a flex row
It can be measured at width 0 and draw "..." in a wide area. Make the box .flex() with .min_w_0(), and avoid percentage upper bounds such as max_w(relative(..)).
Focus
track_focus on the root breaks the window buttons and edge resizing, so use a zero-size focus anchor. track_focus(handle) ignores the element's tab_index; the order lives on the handle. Releasing Enter or Space on a focused element sends a click, so focus returns to the anchor after a mouse click.
Cached views
Only a notified view is rebuilt, and a notify on the root does not update its children. Do not nest cached views. window_control_area hit areas are not replayed from the cache, so the title bar stays outside it.
Shadows
A shadow with zero blur is not drawn, and a shadow on a transparent element paints its inside. Use a ring border instead.
Absolute elements
An .absolute() element without a corner (top_0().left_0()) is placed where it would be in the flow, below the previous sibling.
Images
When an image first loads, only the first view that asked is notified, so a bulk refresh happens when covers arrive.
Mouse wheel on Windows
The wheel is always ScrollDelta::Lines; touchpads arrive as fractional lines.
