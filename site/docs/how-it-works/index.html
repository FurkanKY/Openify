How Openify works

Openify is a native Windows Spotify client written in Rust. Its UI, playback engine and audio output communicate through channels and a ring buffer.

The big picture

gpui draws the interface; librespot 0.8 handles playback. Tokio runs async work, and bundled SQLite (rusqlite) stores caches and queues. Releases target x64 and ARM64 with separate update channels. Playback requires Spotify Premium.

The UI sends commands to the engine and renders events. User-facing messages belong in the UI's translation table. The audio callback must not lock, allocate or wait, and library edits must reach disk before Spotify.

Separate runtimes keep library refreshes from delaying audio-key replies. openify <track link> plays in a terminal with its own runtime; openify logout clears the saved login.

The UI and engine boundary

src/engine/mod.rs defines Command, Event and PlaybackEvent. The handle sends without blocking and retains event senders across restarts. Request keys or sequence numbers let the UI reject stale replies.

Playback core

engine/playback/ makes playback decisions through PlayerPort; tests substitute FakePort. User commands prepare output before commanding the player. Automatic transitions preserve queued audio; a handover gate delays title and cover changes until the next track becomes audible.

Audio-key failure triggers a reconnect and one retry of the same song. Another failure skips the song; the fourth consecutive failure stops playback.

Spotify Connect

Connect is on by default; Settings lets you disable it or rename the device. Local playback uses Openify's queue. Playback started or transferred from a phone uses Spotify's queue and progress through Spirc. When another device plays, Openify shows its status and offers “play here”. Disabling Connect prevents device registration.

The audio path

The custom output replaces librespot's stock backend, whose roughly 0.6-second queue delayed controls. Decoded audio feeds the level analyzer and writer, then an atomic ring buffer and the audio callback.

  • The writer targets 120 ms of queued audio by default. An underrun produces silence and increases the target.
  • Atomics control a short pause fade, seek and manual track-change flushes, and a roughly 10 ms volume ramp. Volume follows the queue, leaving the level display independent of listening volume.
  • A roughly 4-second track-end buffer absorbs decoder delays. The handover gate keeps the UI aligned with audible playback.
  • Crossfade overlaps up to 12 seconds on the writer side, only at natural transitions between different albums. Same-album neighbours, repeat-one and manual changes do not overlap.
  • AutoMix chooses overlap timing from cached silence, tempo and beat analysis. The ten-band equalizer and karaoke run in the audio callback; disabled processing has bit-identical bypass tests. OPRA headphone profiles download on first use.

Cached content appears before background refreshes. library.db also holds local history, pins and hidden songs; these cannot be rebuilt from Spotify.

Each SQLite migration updates its schema and PRAGMA user_version in one transaction. Newer schemas are refused without modification. Library and page databases use WAL with one writer and pooled readers; database reads stay off the UI thread.

The edit queue

  1. The UI updates optimistically.
  2. The engine saves the operation in edits.db, then patches memory and cache.
  3. Spotify receives the edit. Success removes it; temporary failures retry with backoff; permanent failures retain a reason in failed.

Pending edits survive restarts, and Ctrl+Z uses the same operations. Artist following uses this queue but remains experimental. Resume state uses a separate Saver: small state rows update about every five seconds; the larger context row changes only when needed.

Talking to Spotify

Librespot handles sessions, playback and metadata. Library reads and edits use Spotify's internal collection and playlist endpoints. Search, Home, Explore and related artists share pathfinder.rs, which discovers and caches persisted-query hashes from Spotify's web player.

The shared gate spaces background requests by two seconds, respects Retry-After, never retries HTTP 429 and opens a circuit breaker after two consecutive 429s. Interactive search bypasses spacing and the circuit breaker but respects the 429 cooldown. Radio, credits and friend activity use separate gates. Friend activity is experimental and off by default.

Pages can fall back to stale cache. Related artists also have a Deezer fallback; lyrics can fall back to LRCLIB. Local playback sends no listening reports to Spotify, so Spotify history and Wrapped may omit it. Playback transferred through Connect may be counted.

Windows integration

src/system/ handles Windows integration; ui/integration.rs connects it to the interface.

  • Media controls, media keys, taskbar buttons and a tray icon control playback. Hidden windows release render surfaces.
  • System theme follows Windows app mode. Autostart uses the per-user Run key.
  • Discord Rich Presence is opt-in and clears during pause or private sessions. It requires a configured application ID; src/discord.rs currently ships with an empty ID.
  • Velopack handles updates. A version becomes healthy after its window stays open for 20 seconds. Two unsuccessful starts trigger rollback on the third start when a previous healthy version is available; the failed version is skipped until a newer release.

How it is tested

cargo test --release runs module tests using fixtures and fake backends. Live-account tests are ignored by default and excluded from CI. Audio tests drive the ring without hardware and check allocation and frame ownership. src/ui/design_rules.rs checks tokens, tooltips and focus order; see design.

Known limitations

  • Engine and Shell remain large. The real librespot session still needs manual playback checks after changes.
  • Connect has limited live testing. Phone volume does not update the UI slider, and phone seeks can leave buffered audio briefly audible. Enabling Connect or renaming its device restarts the session.
  • Screen readers cannot read the interface because gpui lacks Windows UI Automation support.
  • Undocumented Spotify endpoints can change or stop working.
