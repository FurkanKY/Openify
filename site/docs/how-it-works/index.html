How Openify works

Openify is a native Windows Spotify client written in Rust. This page walks through how the process is laid out, where the boundaries are, and why some parts look the way they do.

The big picture

The UI is built with gpui, the UI framework from Zed. Playback comes from librespot 0.8. Async work runs on tokio, and SQLite (rusqlite, bundled) holds caches and queues. Release builds target x64 and ARM64, each with its own update channel.

The app splits into two halves that talk through channels. The UI thread renders and handles input. A separate engine thread owns the Spotify session, the player and the databases. The audio device is fed from a lock-free ring buffer.

Four rules hold the design together:

  1. The UI never touches librespot, the network or the engine's state. It sends commands and renders events.
  2. The engine never produces user-visible text. It sends typed codes, and the UI turns them into strings.
  3. The audio thread never takes a lock, allocates or waits.
  4. User data in the edit queue is saved to disk before it is sent to Spotify.

Threads and runtimes

There are two runtimes on purpose. librespot waits only a short time for the answer to an audio-key request. When heavy work such as the startup library refresh shared workers with the session, the answer was not read in time and tracks failed to start. Now heavy work cannot starve the connection.

Running openify <track link> skips the UI and plays in a terminal. openify logout clears the stored login.

The UI and engine boundary

The whole contract lives in src/engine/mod.rs. The UI sends a Command through a non-blocking handle. The engine answers with Event and PlaybackEvent values. Answers echo the request's sequence number, so the UI drops stale results. The handle keeps the sender halves of the event channels, so the UI's listeners survive an engine restart.

Decisions that need no I/O live in pure modules with unit tests: the play queue, recovery policy, the login state machine, and reconnect and account checks.

Playback core

Everything that decides what the player does sits in engine/playback/, behind a test seam. PlayerPort describes what the engine asks of the player. The real implementation wraps librespot, and tests use a fake that records calls. A few rules it enforces:

  • A user command touches the output first, then the player. An automatic track change never flushes, which keeps playback gapless.
  • After a key failure the engine reconnects and retries the same song once. A second failure skips, and the fourth stops.
  • A handover gate holds back UI events until the new track is actually audible.

Spotify Connect

Connect is on by default and can be switched off in Settings. Whoever started playback drives it. If a phone starts or transfers playback, Spotify owns the queue and progress, and Openify only observes and runs the audio output. If another device plays and nothing plays here, Openify shows that and offers "play here". Otherwise Openify uses its own queue and rules. With Connect off, no Connect device is registered, and unit tests pin that.

The audio path

Openify replaces librespot's stock rodio backend. The stock backend keeps about 0.6 seconds of audio queued, so pause, seek, track change and volume all felt late. The replacement works like this:

  • Decoded audio goes through a sink that feeds a level analyzer (the equalizer bars) and a writer that pushes frames into a ring buffer.
  • The ring uses atomic counters, with no unsafe, no locks and no allocation on the audio thread.
  • The writer waits until the queue drops below a target, 120 ms by default. If the ring runs dry mid-stream, the source plays silence, counts an underrun and raises the target.
  • The engine controls output through atomics: a short fade before pause, a flush on seek or track change, and a volume ramp of roughly 10 ms. Volume is applied after the queue, so the equalizer bars do not flatten at low volume.

At a track's end the ring may hold about 4 seconds, so a stalled decoder cannot cause a gap at the next track. That makes the player run ahead of what you hear, which is why the handover gate exists.

Several features sit on the same output:

  • Crossfade (up to 12 s) overlaps tracks on the writer side. It applies only to natural track ends between different albums. Same-album neighbours, repeat-one and anything you trigger by hand stay gapless.
  • AutoMix decides where and how long to overlap, using silence, tempo and beat analysis cached in the library database.
  • Equalizer and karaoke run on the audio thread. The equalizer has ten filters and automatic pre-gain, and headphone profiles come from the OPRA project, downloaded on first use.

While they are off, their code does not run and output is bit-identical, which golden tests cover.

Persistence

All paths are per user. Only the edit queue and the login are needed for correctness. Everything else can be rebuilt.

WhatWhere
Library cache: library, tracks, lyrics, resume state, pins, local play history, hidden songs%LOCALAPPDATA%\Openify\library.db
Page cache: artist, album, Home, Explore%LOCALAPPDATA%\Openify\pages.db
Covers (200 MB cap), encrypted audio (2 GB cap)%LOCALAPPDATA%\Openify\covers, audio
Settings (JSON with a version field)%APPDATA%\Openify\settings.json
Edit queue (user data, outside the cache folder)%APPDATA%\Openify\edits.db
Spotify sessionWindows Credential Manager, never a file

The library cache is shown instantly at startup and refreshed in the background. Stale pages show first and refresh behind.

Every SQLite file stores its schema version in PRAGMA user_version. Each migration step runs in its own transaction together with the version bump, so an interrupted step leaves no trace. A file newer than the code, for example after an app rollback, is refused and left untouched. Each database has a test that builds every older version and migrates it to the latest.

library.db and pages.db use WAL mode with one writer and a pool of read-only connections, so reads never wait for a writer. The UI thread does no database reads: it gets data from the engine as events.

The edit queue

Library writes such as like, add to playlist, rename, reorder and follow share one flow:

  1. The UI updates its own view immediately.
  2. The operation is written to edits.db.
  3. The engine applies the same pure patch functions to its own copy and the disk cache.
  4. Only then is the request sent to Spotify. Success removes the row. A retryable failure retries with backoff. A permanent failure moves the row to failed with a reason code the UI shows.

A write therefore survives quitting before it reached Spotify, and Ctrl+Z undo is built on the same operations. Resume state (queue and position) is saved the same way, in small rows written about every 5 seconds.

Talking to Spotify

Playback, session and metadata go through librespot. Library reads and edits use the same internal endpoints the official desktop client uses, not the public Web API, so no Web API scopes are needed. Search, Home, Explore and related artists use Spotify's internal GraphQL endpoint, called pathfinder, with persisted queries. The query hashes change when Spotify ships a new web player, so Openify discovers and caches them at runtime. If a call fails, the UI shows the stale cache when there is one, otherwise an empty or offline state.

Openify tries not to hammer Spotify:

  • At most one request per 2 seconds.
  • No retry on HTTP 429, and nothing until Retry-After passes.
  • A circuit breaker after two consecutive 429s in a session.
  • One in-flight request per key, and only what is on screen.

Radio, track credits and friend activity (off by default) use unofficial endpoints that Spotify's own clients use. They are read-only and have separate rate gates.

Local playback sends no listening reports to Spotify, because the vendored librespot code contains no such call. Locally played songs may therefore not appear in Recently played or Wrapped. This has not been checked against a live account. Playback driven by a phone through Connect may be counted by Spotify. Openify is not affiliated with Spotify AB.

Windows integration

The src/system module is OS-facing and knows nothing about the UI. ui/integration.rs bridges it to the app through a channel.

  • Media controls: System Media Transport Controls (volume flyout, lock screen, media keys) and taskbar thumbnail buttons.
  • Tray: closing the window hides to the tray, and hidden windows release their render surfaces to keep memory low.
  • Theme: the System theme reads the Windows app color mode without modifying the registry and follows changes live.
  • Discord Rich Presence: opt-in, and silent during private sessions and pause.
  • Autostart and updates: "start with Windows" uses the per-user Run key. Updates use Velopack. If a new version does not prove itself healthy (window open and 20 seconds without a crash) over its first starts, the app rolls back to the last good version and skips the bad one until a newer release.

Vendored patches and why

Four crates are patched copies in vendor/, wired in through [patch.crates-io]. Every changed line is tagged OPENIFY:, and each directory has an OPENIFY.md with the rationale.

librespot-coreAudio-key requests wait 4 s and retry up to 3 times with backoff.Under load Spotify delays key requests. Upstream gave up after 1.5 s and the track never started.

A script checks drift against crates.io, and CI runs it in summary mode. See the contributing page for how to work with it.

How it is tested

Tests are plain cargo test unit tests inside the modules. They use recorded fixtures and fake backends and never touch Spotify or your real settings. Tests marked #[ignore] hit a real account, run by hand only and never in CI.

  • Pure core, thin shell. Decisions are side-effect-free functions. I/O stays at the edges behind small seams such as PlayerPort.
  • Deterministic audio tests. The ring is driven without a sound card. Tests check that the audio thread does not allocate and that the writer never touches frames the device is about to read.
  • Design-rule tests. Count-based tests in src/ui/design_rules.rs must stay at zero: spacing, radius, font size, shadow and color values come only from theme.rs, and every icon-only button needs a tooltip. See the design page.

Known debt

  • Engine, Shell and a few files such as output/ and edits.rs are still large. New features are separate gpui entities rather than new Shell fields.
  • The player has a test seam, but the librespot Session does not. Changes need a manual check of gapless transitions, pause or seek during a handover, and key-failure recovery.
  • Persisted-query hash discovery is duplicated in four places, and search does not use the shared rate gate yet.
  • The engine still produces some user-facing text while the i18n migration finishes.
  • Vendor drift is checked by script but not enforced.
  • Connect passed a first live check. Transfer-here, phone volume and on/off/on were not checked separately. Known limits: the phone's volume reaches the output but not the UI slider, the queue panel shows Openify's own queue while the phone drives, and turning Connect on or renaming the device restarts the Spotify session once.
